# MaxAgent 與 Codex 原對話派工調查總結

> **2026-11-18 導讀：本文保留早期調查，不可直接把下方「目前不能派工」當作最新狀態。** 後續已接入原佇列及特定版本的桌面持有者通道，並有佔用時換模型與同輪結果的真實證據。請先讀 [工具能力與已查限制](06-工具能力與已查限制.md) 及共用進度，再按本文查早期路線。不要因此重做獨立恢復、隔離副本或相同 daemon／proxy 測試。

更新：2026 年 11 月 14 日。本文整理目前專案中的既有調查和實測；未重新執行這些實驗。適用於本機 Windows 和當時使用的 Codex 版本，不代表其他版本永遠如此。

## 先看結論

**目前 MaxAgent 可以讀取 Codex 的舊對話，也曾向部分舊對話成功派工；但當某個對話已由另一個 Codex 程序持有寫入權時，MaxAgent 的直接派工仍會失敗。這個問題尚未修復。**

目前派工的方式是：MaxAgent 另啟一個 Codex 程序，要求它恢復指定原對話，再開始新任務。若原對話已有另一個寫入者，Codex 會拒絕恢復；這個拒絕發生在任務送出之前。讀取本機歷史不需要取得同樣的寫入權，所以「能看到對話」不能證明「一定能派工」。

重點是：下表有些方法**實際被拒絕**，另一些只是**尚未驗證**。後者不能說成已經失敗，也不能說成已經解決問題。

## 我們實際遇到甚麼

- 「Say hi」曾回覆 `already has an active writer`。Windows 的唯讀診斷在當時查到持有寫入鎖的是 Codex 桌面程式的子程序；這只代表當時狀態，不代表每次都是同一個程序。
- 「绘制奇幻飞行 2D 动画」在選擇不同模型後重新測試，仍在恢復原對話時被拒；**該次新測試任務沒有送出**。這證明換模型沒有解除當次佔用衝突。
- 另一個既有隔離測試對話曾在換模型後真實續派並讀回結果。這證明部分對話的流程可行，但不能推論被佔用對話也可用。
- 原對話中另有一筆「hi」曾寫入紀錄，但沒有找到其正式回覆。這和上面被拒絕的新測試是不同兩筆，不能把兩者混為一談。

## 已查過的方法

### 1 另啟 Codex 程序並恢復原對話

**想法：** 沿用目前 MaxAgent 的做法，啟動自己的 Codex app-server，傳入原對話 ID 後派工。

**結果：部分可用；被佔用的對話實際失敗。** 某些舊對話已實測可續派；目標對話有寫入者時，恢復請求返回錯誤 `-32600`／`already has an active writer`。因為還沒開始這一輪，這次任務確定沒有送出。這不是單靠視窗開著就能判斷的；實際證據是 Codex 的拒絕及當時的鎖持有者診斷。

**限制：** 只換模型不能解除對話的寫入衝突；登入、模型權限或額度則是另外可能出錯的環節。

### 2 先讀本機歷史、再由獨立程序接回

**想法：** 既然 MaxAgent 能讀到舊紀錄，是否就能操作同一個對話？

**結果：可讀取歷史；無法單憑讀取證明可派工。** 本機紀錄提供對話 ID、工作目錄及訊息，但目前負責寫入的程序仍可能拒絕另一個程序恢復該對話。

### 3 在隔離副本恢復相同 ID

**想法：** 複製紀錄到隔離環境，檢查 Codex 是否能恢復相同的對話 ID。

**結果：隔離副本可恢復；不代表原對話已修好。** 副本沒有複製原對話當時的寫入鎖，所以此測試只能說明副本恢復流程可行，不能說明被佔用的正式原對話可以接管。

### 4 連到已運作的共用 daemon／proxy

**想法：** MaxAgent 和 Codex 使用同一個後台服務，避免各自啟動程序爭取寫入權。

**結果：本機尚未接上目前的桌面持有者。** 之前檢查的預設控制入口不存在或無法連線；當時桌面 app-server 使用標準輸入／輸出（stdio），由桌面程序持有。本機後續版本的程序檢查未看到明確的 `--listen` 參數；這不能證明不存在其他入口，但也不能證明獨立 MaxAgent 能連上。

`codex app-server proxy` 需要有可連接的控制 socket；沒有能對上目標桌面程序的入口，單靠 proxy 不能證明已接通。[官方 App Server 文件](https://learn.chatgpt.com/docs/app-server)說明了 stdio、Unix socket 和實驗性 WebSocket，但此前未找到把第三方程序接入現有桌面私有 stdio 的受支援步驟。

### 5 參考 T3 Code 的 proxy 與訊息格式轉接

**想法：** 沿用 [T3 Code Windows 案例](https://github.com/pingdotgg/t3code/issues/28678)，將不同格式的訊息轉接，連到已運行的共享服務。

**結果：別人的環境有成功回報；本機沒有證明成功或格式不相容。** 該案例使用已存在的共享 daemon。本機首先卡在沒有找到可接到目標桌面程序的入口；當時在 Windows 的假 socket 實驗也因 `EACCES` 未能完成握手。因此不能說本機格式已證明不相容，也不能把他人的結果當作 MaxAgent 已修復。

### 6 以 `codex queue` 排入原對話

**想法：** 不直接接管寫入權，先把新任務放進待處理佇列，由持有該對話的 Codex 程序取走。

**結果：有官方程式碼和命令可研究；本機尚未驗證桌面會接收。** 官方程式碼顯示，在特定條件下，已載入對話的服務會檢查外部佇列；但沒有確認本機桌面程序使用同一份佇列，以及如何可靠對上「排入、接收、該輪完成」。之前沒有向真實佇列寫入任務。

**重要限制：** 命令成功只能表示排隊操作沒有報錯；`--resume` 即使未能恢復也可能以成功結束。不能單憑命令結果或佇列項消失，就宣稱原對話收到或任務完成。佇列若延遲消費，也需處理意外稍後執行、取消和避免重送。參考 [Codex CLI 文件](https://learn.chatgpt.com/docs/cli/reference#codex-queue)。

### 7 MaxAgent 與 Codex 終端版共用同一服務

**想法：** 另外建立雙方都能連接的服務，再讓終端版和 MaxAgent 連到它。

**結果：另一種待實測使用模式，並非目前桌面衝突的修復。** 理論上可研究共用服務與原 ID 恢復；仍須驗證帳號、權限、原對話可否恢復及訊息格式。它不能直接接管眼前已由 Codex 桌面持有的對話。

### 8 使用 Codex 內建工具讀取對話

**想法：** 利用 Codex 本身提供的對話管理工具確認原 ID。

**結果：在 Codex 內的只讀查詢有證據；獨立 MaxAgent 接入未證明。** 能在本 Codex 會話使用的工具，不等於獨立 Windows 程式可以調用同一通道，也不等於已能派工。

### 9 手動備案：複製任務並開啟原對話

**想法：** 確定任務沒有送出時，先複製草稿，再向 Windows 提出開啟原對話的請求，讓使用者自行核對、貼上和送出。

**結果：已實作手動備案；不是自動派工。** 本機替身驗證了原對話 ID、複製及錯誤處理。Windows 接受開啟請求，不保證視窗一定已切到指定對話；真實開啟行為仍有待確認。結果未確認時不應以這個備案假定可以重送。

## 程序和記憶體

MaxAgent 的 Codex 派工完成或失敗時，程式會要求它啟動的 Codex 子程序結束；取得模型清單的程序也會結束。

2026 年 11 月 14 日，使用者同意後，在既有隔離舊對話送了一條**新的**短任務。任務結果在同一原對話核對完成；約每 1.2 秒採樣時，共觀察到 10 個程序，合計私有記憶體採樣最高約 190.6 MiB。任務完成約兩秒後，這次已觀察到的程序均已退出。

這是一次實測，不包括 Codex 桌面版和 MaxAgent 本體；短時間存在的程序可能被抽樣漏掉。不能據此保證所有真實任務都沒有殘留，或把該數字當成全部情況的最高記憶體。

## 現在可以怎樣使用

1. **確定沒送出且顯示寫入衝突：** 可以使用「複製任務並開啟 Codex 原對話」。確認對話正確後，自己貼上和送出；如沒有跳到原對話，自行在 Codex 選回它。
2. **可能已送出、結果未確認：** 先重新讀取原對話並查看狀態；沒有足夠證據前，不應自動重送。
3. **模型無法使用：** 這與寫入衝突是不同問題。對話可能已收到訊息，但模型、帳號或連線未能完成；需看該輪的具體錯誤。

不要以刪除鎖檔、強制結束不明程序或建立新對話來冒充修復；這可能打斷現有工作或失去原對話的上下文。

## 值得繼續研究的方向

1. **優先：受支援的桌面共用入口。** 若新版 Codex 文件、工具或程式提供明確入口，先只讀核對它是否連到正在持有目標對話的桌面程序及同一原 ID，再處理派工與結果。
2. **佇列方向。** 先確認實際桌面持有者是否讀同一佇列，再設計逐項接收、完成、取消、逾時和避免重送；沒有證據前維持未驗證。
3. **資源量測。** 對更多真實任務、錯誤及中斷情況追蹤 MaxAgent 啟動的完整程序樹，分開計算 MaxAgent、Codex 桌面和任務程序，才可評估是否有穩定殘留或節省記憶體。

## 補充參考：微信和飛書如何接 Codex（2026-11-14）

這一節是閱讀公開專案後的整理；沒有安裝、執行第三方程式、修改設定、發送訊息或呼叫模型。專案作者的描述不等於本機實測結果。

### 微信：codex-weixin 使用自己管理的長期 Codex 程序

[codex-weixin 說明文件](https://github.com/XavierJiezou/codex-weixin/blob/main/README.md) 描述：使用者的微信訊息先交給本機橋接服務，服務在第一次收到任務時啟動一個長期運行的 `codex app-server --stdio`。橋接服務記錄每個微信使用者對應的 Codex 對話 ID，後續訊息交給該服務管理的對話；其網頁和微信也能繼續相同的受管對話。app-server 啟動、握手或處理請求失敗時，文件表示會退回 `codex exec`／`codex exec resume`。

對 MaxAgent 的啟示：可研究由 MaxAgent 重用一個自有 Codex 程序，避免每次派工都啟動新程序。**但這不等於連到你已經打開的 Codex 桌面程序**：如果桌面程序持有原對話，另一個長期程序恢復同一 ID 仍可能遇到寫入衝突。也不可直接照搬「請求失敗後自動切換並重試」：若任務可能已送出，自動重試可能造成重複派工。

### 飛書：Codex Remote Feishu 使用橋接與代理

[使用者提供的飛書教學](https://ai-bot.cn/codex-feishu-guide/) 實際使用的是 [kxn/codex-remote-feishu](https://github.com/kxn/codex-remote-feishu)。專案的[架構文件](https://github.com/kxn/codex-remote-feishu/blob/master/docs/general/architecture.md)描述：飛書訊息先到橋接服務，再經由代理（wrapper）與 Codex app-server 溝通；代理負責啟動真正的 Codex 子程序、轉送其標準輸入／輸出，並向橋接服務轉交事件和命令。

它對 VS Code 的整合是另一項可選功能：文件要求先退出 VS Code，安裝 managed shim 後重新開啟；架構文件也提到處理編輯器設定或擴充套件入口。這表示代理需要放在相關程序的啟動路徑中，**不能直接推論它能接入已在運行的 Windows Codex 桌面版程序**。目前沒有在本機安裝或測試，未核對它在目標桌面對話被佔用時能否派工。

### 其他可研究方向：CodexHub 的遠端控制方式

公開專案 [CodexHub](https://github.com/happy-loki/codexhub/blob/main/README.en.md) 自述使用 Codex 的遠端控制路徑，讓 Codex App 透過 WebSocket 向其本機後端連接，再交給通訊工具。其文件要求寫入 Codex 設定、重新啟動 Codex 並啟用遠端控制，也描述了本機認證資料及模型流量設定；這與免設定接入目前已運行程序不同。

這值得作為**未驗證的研究方向**，但目前不能把第三方自行實作的協定、認證或路由稱為 OpenAI 對此整合的官方支援，也不能認定它已在本機成功接到同一桌面對話。要評估時需先核對本機版本、授權流程、資料去向、原有模型供應商及設定能否保留、重新啟動的影響，以及同一 ID 的接收與完成；未經使用者同意不改 Codex 設定、憑證或安裝第三方程式。

### 對目前問題的判斷

微信案例證明「橋接服務可以管理自己的 Codex 對話」，飛書專案展示「在啟動路徑中加入代理」的做法；兩者都**尚未證明**獨立 MaxAgent 可以直接接入已被現有 Codex 桌面程序佔用的對話。下一步應先把「共用受管新程序」和「連到已開啟的桌面程序」分開驗證，並沿用原對話 ID、結果確認和不自動重送的要求。

## 補充研究：本機現有能力與下一步（2026-11-14）

- 本 Codex 工作環境提供 `codex-app-tools` 的 `list_threads`、`read_thread` 及 `send_message_to_thread` 等能力。這輪只用 `list_threads` 唯讀檢查「绘制奇幻飞行 2D 动画」：Codex 工具及 MaxAgent 各找到一筆，兩者的原對話 ID 相同。當時工具回報 `notLoaded`；該值不能證明完成，也不能推斷派工一定可行。
- 這證明目前 Codex 內的工具與 MaxAgent 可辨認同一原 ID，且工具清單有對既有對話發訊息的操作；本次沒有調用發訊息工具或測試被佔用對話，不能聲稱其能繞過本機寫入衝突。工具由 Codex 本會話環境提供；尚未找到讓獨立 MaxAgent 桌面程式調用同一工具的受支援方法，也不能假設 MaxAgent 能直接使用它。
- 按 OpenAI [遠端連線文件](https://learn.chatgpt.com/docs/remote-connections)，Codex 有官方遠端控制／配對功能；該功能是否提供獨立第三方本機程式可使用的受支援客戶端、是否可接上既有桌面原對話與回讀同一輪，仍未證明。[CodexHub 專案](https://github.com/happy-loki/codexhub/blob/main/README.en.md) 自述利用遠端控制和本地服務，但要求修改 Codex 設定及重新啟動，並涉及認證與模型流量配置。這是後續要核查的第三方方案，不等於 OpenAI 官方支援或本機實測成功。
- 既有官方 `codex queue` 是另一候選方向，之前只核對程式碼，未對真實佇列寫入。要先證明桌面持有者會取走訊息並按原 ID、同一輪確認接收與完成，也要處理未取走的項目及取消，不可把排隊成功當作任務成功。
- 本次只讀研究及記錄；沒有啟動新服務、更改 Codex 設定、發送任務、重送或呼叫模型。

## 補充參考：T3 Code #8259 的寫入者交接（2026-11-14）

使用者提供 [T3 Code #8259](https://github.com/pingdotgg/t3code/issues/8259)。原案例是 T3 在切換其自行管理的 Codex 供應商程序時，舊程序尚未釋放對話，新程序就嘗試接手；議題建議在交接時確認舊程序已停止或釋放，再開始新程序，並處理清理失敗和遲到事件。這是 T3 自己管理兩個程序的交接，不能直接讓 MaxAgent 停止另一個獨立的 Codex 桌面程序。

該議題的另一位使用者也回報 Codex 桌面版與 T3 跨程式競爭：在其 macOS 環境退出 Codex 桌面版後，T3 可繼續同一對話。這與本機遇到的外部持有者相似，但不是本 Windows 環境已驗證的安全交接，也不能保證退出桌面不影響其他任務；本次沒有關閉 Codex、刪鎖或發送任務。

本機唯讀程序盤點當時看到的 Codex app-server 由 ChatGPT 桌面程序啟動，沒有看到由 MaxAgent 作為父程序的 app-server；這只是當下的程序關係，不能單憑它確認目標對話的持有者。之前 `Say hi` 的鎖持有者曾以 Windows Restart Manager 核對為桌面程序，兩次結果不能混為同一次診斷。

核對目前 MaxAgent 程式：恢復原對話被明確拒絕時，會停止該次自行啟動的 Codex 程序，標記未送出並提供手動備案；`desktop/dispatch-boundary.test.js`、`codex-error.test.js`、`manual-fallback.test.js` 六項本機替身測試通過。這不代表已能安全要求桌面程序釋放對話或共用其程序；被桌面持有的原對話派工問題仍未修復。

## 補充研究：配對遠端控制（2026-11-14）

### 本機直接派工：補充外部證據

使用者要的是同一台電腦上由 MaxAgent 向已開啟的原 Codex 對話派工，遠端配對不是使用者所要求的方案。[Codex discussion #46797](https://github.com/openai/codex/discussions/46797) 有開發者回報：Codex 桌面內的 `send_message_to_thread` 可以向其桌面持有的原對話送訊，但獨立程序另起 app-server 時遇到同樣的 active writer；該回報並未提供可供獨立 MaxAgent 使用的本機介面。此能力在其他個案也可能遇到寫入衝突，不能保證所有對話成功。

[Codex issue #54683](https://github.com/openai/codex/issues/54683) 的開發者回報 `codex queue` 對已載入對話可能有用，但缺少可靠的接收確認，可能持續排隊；這是外部報告而非本機驗證。未經驗證，不應將排入佇列當作送達或完成，也不能在狀態不明時重送。這輪沒有對真實佇列寫入或修改程式；尚未找到可安全直接接入目前 Windows 桌面程序的受支援本機入口。
