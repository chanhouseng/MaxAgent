# 項目中心工作台：產品設計草案

日期：2026-11-18。開發分支：`codex/project-centered-workspace`。

舊版基準為 `4cdb6d6`，標記 `legacy/pre-project-workspace-2026-11-18`。本文件是新版本的設計草案，不表示以下功能已實作，亦不將尚未決定的建議當成使用者已確認的要求。最新功能實測仍以 `04-實作記錄與進度.md` 為準。

## 1. 使用者已提出的目標

- 首頁以使用者的項目為中心，可選擇項目所在的本機資料夾。
- 新項目一開始沒有 Agent 對話，先顯示類似 Codex 新對話的主輸入區。
- 預設由 AI 安排 Agent 工作；使用者亦可在輸入區選擇具體 Agent 直接交辦。
- 使用者可選擇模型，保留各 Agent 對話供查看、質疑和直接介入。
- 希望沒有 CC Switch 的使用者也能在 MaxAgent 管理模型與連線。
- 先服務一人管理多 Agent 開發，後續再擴展為 OPC 的開發、宣發、內容、營運及回饋協作。
- 保留舊版功能，不回退已有成果。這次只提交舊版、建立分支和整理設計，不發出任何 AI 工作。

## 2. 建議的使用流程

1. 首頁顯示項目卡片：名稱、資料夾、最近活動、進行中與待確認數量。
2. 「新增項目」選擇現有或空資料夾，設定名稱。只登記項目，不啟動模型或修改資料夾內容。
3. 進入項目顯示空白主對話與輸入框，預設收件人為「自動分工」。未配置可用執行工具時先引導設定，不顯示虛假的可用模型。
4. 使用者描述目標，由協調 Agent 判斷應直接回答、追問需求，或提出工作安排。
5. 工作真的派出時，才建立相應 Agent 的工作對話。未派出的角色不預先製造空聊天室。
6. 主對話呈現整體安排、進度、待確認事項與成果；每項工作可打開對應 Agent 對話。
7. 輸入區可選擇已建立的具體 Agent 直接交流，保留主對話返回入口。
8. 人工介入與更改需求要更新同一份工作安排，避免協調者繼續執行過時任務。

項目主對話屬於 MaxAgent 的項目紀錄，不等於將多個外部工具的歷史拼接成一個原聊天室。每個執行工具仍有自己的原會話 ID。

## 3. 三種選擇要分開

| 選擇 | 用途 | 範例 |
| --- | --- | --- |
| 角色 | 工作職責與交付要求 | 協調、開發、測試、審查 |
| 工具 | 實際執行、操作檔案與保留會話的程式 | Codex、Claude Code |
| 模型及連線 | 這個 Agent 使用哪個服務與模型 | 原工具登入，或使用者自行配置的相容 API |

自動分工不等於自動選最昂貴的模型，也不等於每次同時叫出所有 Agent。簡單問題由協調者處理；需要操作檔案才派工作者，需要核對才安排測試或審查。

## 4. 對話由誰管理：產品目標與技術能力分開

使用者認同由 MaxAgent 管理對話是理想目標，但這不表示三種工具的完整管理已可行。已查限制與避免重複研究的清單見 [工具能力與已查限制](06-工具能力與已查限制.md)。

**建議方案：新項目的工作會話從一開始由 MaxAgent 建立並管理；現在的舊聊天室仍保留可打開的位置。** 「保留入口」只表示不刪除、不取消目前看歷史與有限續派的功能，不代表有完整控制權；具體介面位置未定。新模式的工具能力必須逐一實作與驗證，不將這個方向寫成已解決既有桌面控制限制。

- 使用者仍在圖形介面打字、選檔案、看進度，不需要操作終端。
- MaxAgent 統一安排自己管理會話的寫入、模型、排隊和程序生命週期是待開發目標；Codex、Claude、DSH 不能直接當作已具有相同能力。
- 不承諾外部桌面工具可以同時接管這些會話，也不為新項目重新命名、搬移或複製原有聊天歷史。
- 舊對話仍走舊版已存在的接入器與限制；不把新模式宣稱成解決所有舊對話的佔用問題。
- 每種工具必須先驗證新模式的登入、模型、同一會話續接、接收、完成、取消和復原，才允許協調者選用。

另一選擇是全部依賴原桌面對話。這較符合跨視窗直接操作的習慣，但仍受桌面控制入口、佔用與模型切換能力限制，不能當作可靠自動調度的預設前提。

## 5. 自動化與人工確認

建議第一版先提供「先看安排再開始」與明確的項目授權範圍。是否預設直接自動執行，仍需使用者決定。

- 工作安排包含目標、負責 Agent、前置工作、預期成果及驗證方法。
- 一般已授權的讀檔、編輯與本機測試按安排執行；需要使用者決策、外部發布、付費或超出授權時，集中提出具體問題。
- 使用者介入正在工作的 Agent 時，不偷偷插入第二筆寫入；依工具能力提供等待、追加指示或取消，並清楚說明影響。
- 失敗不自動重送原任務、不擅自換模型或新開替代會話。
- 是否允許有限次數的自動修正，應另設明確政策；初版不讓 Agent 自行無限迴圈。
- 使用者說「停止項目」時先停止新增派工，再分別確認執行中工作的取消結果；不能只把畫面改成停止。

## 6. 任務與結果的共同規則

建議工作狀態：待安排、等前置工作、準備中、等待接收、已接收執行中、等待使用者、已完成、失敗、取消待確認、已取消、結果未確認。

- 每筆工作有穩定的 projectId、taskId、attemptId；每次對外操作先持久保存識別，再送出。
- 工具會話 ID、工具本輪 ID、接收證據、正式結果及完成證據各自保存。
- 程序啟動、寫入通道成功、排隊成功都不能單獨當作工作已接收。
- 同一輪任務完成與項目目標完成是不同層次。協調者必須按驗收條件彙整成果，不能因工作者說完成就宣稱整個項目成功。
- 重啟只恢復紀錄並核對狀態，不自動重新派出未確認工作。
- 主對話與 Agent 對話只引用同一份工作狀態，避免再建立互相矛盾的狀態清單。

## 7. 多 Agent 操作同一項目

不能讓多個 Agent 任意同時改同一工作目錄。建議第一階段對同一項目的檔案修改採串行安排；讀取與審查是否可並行，依快照及工具能力開放。

後續有 Git 的項目可加入獨立工作目錄／分支、差異審查與合併；無 Git 的項目先保持單一寫入者，不暗中替使用者初始化 Git 或移動檔案。合併衝突、失敗測試及不符合需求均應回到同一工作安排。

附件需明確顯示將提供給哪個 Agent／供應商；不能把整個資料夾或其他 Agent 的完整對話預設上傳。對外派工內容由目標、必要背景及必要檔案組成，不無限制複製歷史。

## 8. 內建模型與連線管理

這部分是 MaxAgent 的獨立功能，不要求安裝 CC Switch，亦不覆寫 CC Switch、Claude 或 Codex 的共用設定。

- 每個連線保存名稱、相容協定、端點及受保護的憑證參照；金鑰不回傳畫面、不進命令參數或日誌。
- 原工具登入與自備 API 是不同方式；不能假定訂閱等同 API 使用權限，也不能把不同公司的模型名稱任意塞入工具。
- 每個角色／工作會話可選連線及模型；每輪送出時固定選擇並核對有效性。
- 更換連線重新查模型，舊清單不可沿用。無可靠清單時標示來源與未確認狀態；實際接受以正常派工回報為準。
- 模型列表可顯示「服務回報」「手動填寫」「已在正常使用中成功」的不同證據，不將列在清單等同有額度或可成功呼叫。
- 憑證安全儲存與連線衝突未解決前，不開放自訂連線派工。沿用舊版 MAX-013A 的阻塞證據，不能假定已有逐聊天室金鑰隔離。
- 暫不需要先造完整的本機代理。先確認各工具能否使用獨立程序設定；確實有必要才另外設計代理的協定、授權及資料處理。
- 內建連線管理不會解鎖已開啟的 Claude 桌面原對話換模；此項依使用者指示暫停。

參考：CC Switch 官方專案 https://github.com/farion1231/cc-switch ；Claude Agent SDK https://code.claude.com/docs/en/agent-sdk/typescript 。這些是技術調查來源，不是 MaxAgent 已實作的能力。

## 9. 建議的開發批次與完成標準

以下先界定交付邊界；需要確認第 4、5 節後，再拆成可直接執行的詳細開發計劃。

| 批次 | 建議涉及檔案 | 交付與完成標準 |
| --- | --- | --- |
| P1 項目資料與入口 | 新增 desktop/projects/store.js、store.test.js；main.js、preload.js、index.html、renderer.js、style.css | 選資料夾、建立／重開／切換項目；空項目沒有假對話；同一實體資料夾避免重複登記；舊對話入口完整保留；只移除登記不刪使用者資料夾。 |
| P2 主對話與單一受管 Agent | 新增 desktop/projects/conversations.js、desktop/agents/runtime.js 及對應測試；接既有 UI 和派工儲存 | 先核對一種工具的相容版本及能力。可以正常建立受管工作會話、續接同一 ID、區分接收與結果、重啟不重送；沒有可靠能力就明確阻擋，不顯示假執行。 |
| P3 角色與模型連線 | 新增 desktop/agents/registry.js、desktop/connections/store.js；沿用 model-settings.js、preload.js 和既有設定入口 | 對話各自選模型／連線；使用假憑證及替身程序核對隔離、失效攔截與安全儲存；不改外部共用設定。真實採用待另外授權或正常使用證據。 |
| P4 可檢查的工作安排 | 新增 desktop/projects/task-store.js、desktop/orchestration/planner.js 及測試 | 主對話產生結構化工作安排；驗證格式、依賴與權限；初版先確認安排後開始；重複操作不生成重複派工。 |
| P5 調度與人工介入 | 新增 desktop/orchestration/scheduler.js、policy.js；接 runtime.js 及任務狀態 | 同項目修改串行、跨項目有限並行、暫停與取消可追查、工作者對話可檢查；介入更新工作安排，重啟恢復而不重送。 |
| P6 成果及驗證 | 新增 desktop/orchestration/results.js；主對話、任務詳細介面與本機測試 | 保存成果位置、變更和測試證據；任務完成與項目完成分開；失敗／未確認不報成功；使用者能找出每份成果由誰產生。 |
| 後續 | 視前述能力另排 | Git 隔離工作目錄、同項目安全並行、費用控制、多職能角色模板、OPC 營運與手機控制；不混入第一批。 |

新功能以小模組接入，避免把協調、排程和連線都堆進 main.js／renderer.js。既有大檔只負責轉接新模組與畫面，不為新模式重寫舊版工具接入器。

## 10. 驗證及交付規則

- 各批先用本機資料、假工具和隔離設定驗證；npm.cmd run check、npm.cmd test 及該批本機介面檢查通過後，才報告該批完成。
- 涉及真實模型的測試必須另有授權，或使用者本來就要做的工作；本計劃本身不授權任何付費請求。
- 替身通過、真實工具接受、原會話結果成功、完整項目達標分開記錄。
- 這份設計不把舊版未確認事項改成已完成，也不安排重跑 Claude 桌面換模、Windows 通知或 ZIP。
- 待確認的產品決策集中在：新項目是否由 MaxAgent 管理工作會話，以及自動分工開始執行前是否預設先確認工作安排。其餘細節可沿小批次設計逐步收斂。
